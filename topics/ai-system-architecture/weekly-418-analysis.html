1. 如果科技停止在21世纪初 —— 一篇「怀旧文」里藏着一条可计算的工程命题 ​

原文主张（lukaszkups.net，Łukasz Kups，2026-08-29，已一手实抓）

作者的立场比周刊转述的更硬：「我真诚地相信，21 世纪初大概是人类最接近『技术与真实生活完美平衡』的时刻。我们有足够的技术让生活更轻松，但没有足够的技术让它变得烦人——而这个区别很重要。」 他的判据不是「那时更好」，而是技术的位置：技术是工具，不是生活方式。原文的关键句（英→中，按原文意）：

  • 「互联网是一个你去的地方」：坐到电脑前、连接、办完事、断开。「在线」与「离线」之间有一条非常明显的边界——今天这条边界基本不存在了。」 而现在：「你醒来在线、工作在线、边吃边看在线、边走边听在线、睡前刷着在线。」
  • 「一点摩擦反而是好事」：「如果你想拍照，你得带着相机；想听音乐，你得有那张音乐；想跟人说话，你得真的跟他说话。一点点摩擦让事情变得是有意为之（intentional）。」今天一切即时，「听起来很棒——直到一切都变成了噪音」。
  • 「我们优化错了东西」：手机帮你沟通，电脑帮你工作，互联网帮你找信息，数码相机帮你拍照——「这些东西没有一个需要成为你存在的中心」。今天一切为 engagement 优化：更多通知、更多推荐、更多内容、更多个性化、更多自动化，「但似乎没人有兴趣优化这个问题：能不能让我一个人静一会儿？」
  • 甜点区：大概是 2003 年前后（周刊补充了另一个锚点：作者真正想回到的是 2007-06-29 之前，即 iPhone 发布之前）。「现代到足够有用，原始到足够无害。」
  • 诚实的地方：作者自己承认**「显然，我在浪漫化它。21 世纪初也有大量烂技术：慢网、糟糕的手机摄像头、Flash 网站、Internet Explorer，你没法直接问 AI 五秒钟给你解释一件事。」** 但他认为**「也许这才是重点」**。

我的评注

  1. 这篇最容易被误读成「老年人怀念过去」，但它其实提出了一条可操作的判据，而且这条判据可以量化。 作者真正在说的不是年代，而是**「技术的接触面」：2003 年的特征不是「技术差」，而是「技术可以不被携带」——手机是放在家里的、互联网是「某个地方」、社交身份可以随时消失。换句话说，临界点不在「算力多少」，而在「技术是否随身体一起移动」。 真正的分水岭是 2007-06-29（作者自己指认），因为那一天起，技术从「场所」变成了「器官」。这跟本库反复出现的一条线直接接得上：#416/#417 讲的是「执行成本 → 0」带来的后果，本期讲的是「接触成本 → 0」带来的后果**——两者是同一种「边际成本消失」的两个方向（一个消失的是做事的成本，一个消失的是被打扰/被连接的逃避成本）。
  2. 原文里最像工程论文的一条是「friction made things intentional」——摩擦是意图的产生器。 这不是审美判断，而是一个有代价的机制：当你必须携带相机、必须走到电脑前、必须真的打电话，这些动作本身就是一道过滤器，把「想做」和「随手做」区分开。 这与本库 topics/ai-system-architecture/cognitive-atrophy-knowledge.md（摩擦假说 Friction Hypothesis：认知摩擦不是需要消除的障碍，而是认知结构得以维持的前提条件）几乎是同一命题的两个版本——那篇讲的是「消除摩擦导致能力退化（Deskilling）」，这篇讲的是「消除摩擦导致行为失去意图」。合起来是一条完整因果链：摩擦 ↓ → 意图 ↓ → 行为不受意愿控制（上瘾/噪音）→ 能力退化。 周刊本期没把这条链点出来，但两篇文献拼在一起就是完整的。
  3. 必须打问号的地方：作者的因果归因是「技术占据了主导」，但更准的表述可能是「商业模式选择了让技术占据主导」。 技术本身没有「想占据你存在中心」的动机——是 engagement 优化这个目标函数在这么要求（原文自己也写到了：「今天我们为 engagement 优化一切」）。所以这不是「科技停止在哪一年」的问题，而是「谁在选择优化目标」的问题。 一旦把主语从「技术」换成「广告/订阅变现模型」，结论就从怀旧的变成了可行动的：甜蜜点不是某个年份，而是一组约束——不随身的设备、有明确边界的在线状态、不需要持续证明自己有趣的社交。 这三条今天全部可以局部重建（自托管、离线日历、无算法的时间线），只是它们需要「主动抵抗默认设置」，而默认设置永远是最大化 engagement。
  4. 对「外脑」的自我告解：本库本身就是一个 engagement 优化系统的反面——它按需触发（cron 而不是推送）、不制造通知、不要求你持续在线。但它有一个同样的隐患：无限收藏、从不回看。 这一点在 #417 已经用 Overgrown（闲置网页长满藤蔓）记过一次。作者这篇给外脑的提醒是：外脑的价值不在「存得更多」，而在「存下来的东西能在你需要的那一刻出现」——如果它只是把现实世界数字化成一个更大的、更没人看的仓库，那它就是一篇好文章里批评的那种「数字替代品」。

2. 太空机房 —— 谷歌 Project Suncatcher：一首俳句，和一个被电逼上天的赌注 ​

原文主张（智源社区转新智元，2026-11-01，已一手实抓；周刊为转述 + 压缩）

事实链（核对无误）：

  • 谷歌 CEO 皮查伊宣布 Project Suncatcher 完成历史性的「Hello World」时刻。卫星 2026-10-01 搭乘 SpaceX 猎鹰 9 号升空（同一枚火箭还带了 100 多个航天器），入轨后团队花了约 三周 给各子系统上电调试。
  • 星上装载 4 颗谷歌 TPU 芯片，预装开源模型 Gemma 4；但一次只能开 1 颗。工程师发出的第一条提示词是「请以一块绕地球飞行的 TPU 的视角，写一首俳句」，卫星飞越挪威斯瓦尔巴群岛上空时回传：Blue marble below / Data streams in silent grace / Starlight feeds my core.（周刊译作「蓝色星球在下方，数据静静流淌，星光滋养着我的核心」）。
  • 硬件天花板（周刊引用准确）：整颗卫星发电上限约 1 千瓦（≈ 一台电暖器）；受散热限制，TPU 每次只能连续工作约 20 分钟。对比：地面大型 AI 数据中心按几百兆瓦算（1 兆瓦 = 1000 千瓦）。智源原文的比喻更狠：「管这颗卫星叫『太空数据中心』，多少有点像给一间小卖部挂上『宇宙商业中心』的牌子。」
  • 为什么上天：就一个字，电。 谷歌研究团队论文估算，特定轨道上太阳能板发电效率最高可达地面同类设备的约 8 倍（Suncatcher 直译即「捕捉阳光的人」）；SpaceX 今年与 Anthropic 签算力协议时公告写明：训练和运行下一代 AI 所需的算力正在超出地面电力、土地和冷却能给的极限。
  • 两道真正的坎：① 热——太空近真空，没有空气帮忙带走热量，只能靠散热板辐射散热，「不是芯片不行，是热量散不掉」，散热器已是整颗卫星最重的部件之一；② 辐射——高能粒子会造成位翻转（bit flip），「麻烦在于不出声：数据被改坏了，常规监控工具还发现不了」；谷歌在地面粒子加速器实测结论：对推理影响小，对训练影响大。
  • 路线差异（这是本节最值钱的信息）：Starcloud、Cowboy Space 走的是**「一颗卫星一台机器，各跑各的推理」（新智元比喻：天上摆摊）；SpaceX 虽用激光链路但卫星彼此离得太远无法分担计算。谷歌要的是「星间协同计算」：卫星贴近编队飞行（间距仅几百米到 1 公里），用激光互传数据，「像机房里一排排机柜一样合力跑同一个大任务」。难度谷歌自己的比喻：「两颗高速飞行的卫星相隔数公里、双方都在动，还要用光束持续瞄准一枚硬币。」** TechCrunch 评价：在所有太空数据中心构想里，谷歌几乎是唯一这么规划的——别人在天上摆摊，谷歌想在天上盖超市。
  • 时间表：2027 年计划再发两颗卫星验证星间协同；再往后一切都得等星舰（Alphabet 持有 SpaceX 大量股份，两家都把轨道算力押在星舰完全快速复用上）；谷歌研究人员估算星舰要飞一千多次发射成本才能降到位；谷歌给这件事定的时间表是 2030 年代。
  • 补一条周刊未提的历史：这并非人类第一次在太空跑大模型——2025 年 11 月英伟达投资的 Starcloud 已把一块 H100 送上天，一个月后跑通 Gemma，12 月还用莎士比亚作品训练了小模型 nanoGPT。 差别在：去年谷歌的模型在太空，用的是英伟达的芯片；今年从模型到芯片整条链全姓谷歌了。

我的评注

  1. 周刊用这篇做了一个很克制的判断（「这个实验很可能表明『太空机房』不那么可行」），我同意结果、但不同意把结论停在「不可行」。 关键是在这篇里，「1 千瓦 / 20 分钟」不是失败数据，而是「热而非能」是真正的约束。原文把这点讲得比周刊清楚：发电上限 1 kW 与散热 20 分钟是两回事——前者只是小，后者是「算不动」。 这意味着太空机房的瓶颈不在太阳能板面积，而在辐射散热面积——辐射散热功率 ∝ 面积 × T⁴，所以要跑得久就得长更大的散热板、或者把器件温度推高。换句话说：把数据中心搬上天，不是把电的问题外包给太阳，而是把热的问题从「风冷/液冷」换成「辐射」，而后者的热流密度低得多。 这条物理约束比「发了多少电」更本质，周刊没点透。
  2. 本节最有迁移价值的是谷歌那条「星间协同」路线，而且它和本库已有的一条主线是同一件事。 别人做「单星推理」（边缘各跑各的），谷歌做「贴近编队 + 激光互联 + 合力跑同一任务」——这本质上是把「分布式训练/推理的 all-reduce 通信」搬到自由空间光学链路上。它与本库 energysim 里的核心张力完全同构：在一个资源（能源/带宽）受限的系统里，「集中聚合」与「就地分散」哪一个的总代价更低——PyPSA 建模里对应的是输电线路 vs 本地储能，谷歌这里对应的是激光链路 vs 每星一套完整算力。「光束瞄准硬币」这个难度描述，就是「输电线路的线损 + 稳定性」的太空版。 值得在 topics/space-energy/ 记一笔：太空算力的第一性约束可能是「散热面积」，第二性是「星间链路精度」。
  3. 「位翻转不出声」这一点，值得作为外脑的一条工程提醒留档。 原文那句**「数据被改坏了，常规监控工具还发现不了」**——这不是太空独有，它是所有「静默数据损坏」的共性：错误不会被异常捕获，只会被当成正常值算下去。 对本机的直接映射有三处：① 知识库的 md5 校验（topics/ai-system-architecture/brain-self-evolution.md 记过「改动前后输出 md5 逐字节相同」的同构接口）正是这类防御；② state.db 与 journal 的增量处理依赖「时间戳/顺序」正确——若某条记录被静默改坏，增量逻辑不会报错，只会算错；③ PyPSA 的输入参数（如电价、风速序列）若被静默截断，仿真结果「看起来正常但全错」。 谷歌的选择很有信息量：对推理影响小、对训练影响大 —— 因为训练要跨长时间窗口反复读同一份权重，推理只是单次前向，位翻转的暴露面小得多。同理：外脑的「一次性提炼」（推理）比「长期索引/知识图谱」（训练）对静默损坏更鲁棒——这也解释了为什么 links/links.md 这类长期累积资产最该做校验。
  4. 对用户工作流的实际相关性（不牵强，但要如实说）：这条新闻与用户的风电 / PyPSA 能量仿真有真正的概念接口，但不是「能接入」那种接口——它是一条范式记录：当「用电大户」开始把负荷挪到电力最富余的地方（太空 → 近乎持续日照的轨道），能源系统规划的目标函数就从「在负荷侧找电源」变成「把负荷搬到电源侧」。 这与本库 topics/space-energy/lunar-industrial-satellite.md 的「用太空的持续性日照替代地面的间歇性」是同一逻辑，只是从「工业卫星」下移到了「算力卫星」。结论：记录、不跟进（2027 才发第二颗，时间表 2030 年代，对当前工作流无操作价值）。

3. JS 框架的 AI 成本 —— 有人终于给「哪个框架更适合 AI」做了对照实验 ​

原文主张（Nolan Lawson，2026-10-28，已一手实抓）

作者的动机：「Web 开发社区很多决策是『凭感觉（vibes-based）』的」——框架「blazing fast」、工具会「supercharge」你的开发，「所有这些气喘吁吁的吹嘘通常不含任何证据」。在 agentic 时代，「前端被重写，理由是某个框架『对 agent 更友好』（有人想到去问问 agent 吗？）……又是没有证据的断言。每读到这样的说法我就想：基准测试在哪？」 于是他自己写了一个基准。

方法（一手）：用 PokéAPI 设计一个简单但非平凡的应用 → 让 agent 用不同 JS 框架/元框架（Next.js、Nuxt、SvelteKit 等）构建 → 用一致性测试套件检验输出（防止 agent 作弊） → 从 开发耗时、Token 消耗、代码行数、Lighthouse 性能与可访问性 四个维度评估。细节：每个框架用官方 MCP 或 skills（避免「训练数据里没有所以不公平」的指控）；不规定 SSR/CSR 架构、不要求追求极限性能；把 spec 交给 Opus 5.5（high effort），只说「用该框架最新版」；agent 在沙箱里跑，且不知道会被 Lighthouse 测性能；不用 Tailwind/Bootstrap 等组件框架；每个框架取 5 次运行的中位数。

  • Angular 还有一个更实质的失败：两次运行中 agent 建出的 SSR 应用拒绝非 localhost 访问（尽管指令明确说了应用会在反向代理后面），作者判定**「这是有效的不遵守 spec」**，决定不重跑；因此代码量与性能指标只用了 3 次迭代，但成本部分报了全部 5 次。
  • 反直觉的一条：「Vanilla」（纯 JS/TS + Vite，无 UI 框架）表现不如多个框架——原文措辞：「这似乎说明，有一点框架比什么都没有更好（或者说比裸 Vite 好）。」
  • Lighthouse 的性能/可访问性分数几乎饱和（多数 100/100），所以真正有区分度的是「JS 传输字节数」——而它基本就是客户端框架体积的函数。
  • 关于 AI 工具本身的一句狠话（原文结论段）：「我强烈怀疑，当前这一批 MCP 和 skills 可能做的坏事比好事多」；工具使用情况也是散乱的：Nuxt 的 MCP 从未被 agent 用过；Next.js 的 skill 文件只在 1/5 次被读到、AGENTS.md 只在 2/5 次；TanStack Start 的 skill 文件只在 2/5 次被发现。
  • 作者诚实的边界：这是单一「holotype」应用（偏内容型，更像维基而非 Figma/Gmail）；LLM 是随机词生成器，方差很大（有时低掷骰导致 agent 跑偏烧 token，与框架无关）；Lighthouse 本身也不稳定。他的目标不是给出「该选哪个框架」的终极答案，而是证明「在 AI 编码时代仍然可以基于证据而不是感觉做决策」。

我的评注

  1. 这篇文章的真正价值不在排名，而在它把「框架选型」从品味问题变成了成本问题——而成本可以记账。 前三名稳定在 Hono+htmx / Astro / Nuxt，垫底稳定是 Angular，且原因被定位到代码量（2009 行 vs 1370 行）——「代码量 ↑ → token ↑ → 每次后续编辑都更贵」，这是一个乘性的成本。原文引 Rich Harris 那句**「框架不是组织代码的工具，是组织心智的工具」，然后加了一层 AI 时代的推论：代码量直接影响 token 数，包括未来的每一次修改，也就是影响一个代码库随时间维护的真实成本。 这与本库 `#415「生成便宜 ≠ 维护便宜」是同一条线的量化版：AI 让「初次生成」变便宜，但它没有让「后续维护」变便宜，而维护成本正比于代码量**。所以 AI 时代的框架选型标准，第一次变成了「能不能让 AI 少写」。
  2. 「Vanilla 不如有框架」这条最反直觉，但正确解读是：它不是「框架比无框架好」，而是「常识/约定比自由好」。 给 agent 一个有既定模式、有官方 MCP/skill、有协议约束的环境，它的搜索空间被收窄了——这解释了为什么 Hono+htmx / Astro / Nuxt 领先（都是约定强、边界清楚、文档成体系），而 Angular 垫底（抽象层厚、样板代码多、让 agent 写更多行）。对本库的直接启示：给 agent 的「约束」不是限制它的能力，而是降低它的方差。 这与 #417 的「授权粒度」是同一枚硬币：越是自主的 agent，越需要更厚的护栏。 作者那句**「我怀疑当前这批 MCP 和 skills 可能做的坏事比好事多」，正是因为这些工具没被用上（Nuxt MCP 从未用、Next.js skill 只读 1/5）——装了却不生效的护栏 = 零护栏 + 额外复杂度。**
  3. 要泼的一盆冷水：这个基准的「可迁移性」被作者自己限定得很窄，别拿它做架构决策。 它测的是一个内容型小应用（更像维基），而Lighthouse/Core Web Vitals 本身偏向 MPA、惩罚 SPA（原文自己承认：「MPA 框架几乎保证在 TBT、JS 字节等指标上赢」）。真正有区分度、且不受这个偏置污染的两个指标是「成本」和「代码行数」——而这两个恰好都指向同一个结论：代码量。 所以这份实验最可信的用法不是「选 Astro」，而是「把代码量纳入选型的成本函数」。
  4. 对用户工作流而言，这篇有一个非常具体的接入点：用户的 website/（知识库阅读站） 和自托管入口是真实在跑的 Web 项目。这项实验给出的可操作判断是：① 若这些前端未来要交给 agent 维护，选约定强、体积小的方案（htmx/Astro 类）比大框架更省长期成本；② 更值钱的不是换框架，而是「让 agent 少写代码」——这直接对应本库 scripts/ 的模块化与 dsh-archify 那类 skill 化封装。 需要诚实标注的是：这是「可借鉴的判断」，不是「已验证的结论」——它只在「一个内容型应用、Opus 5.5、5 次中位数」这个条件下成立。

4. 本周软件：MonKeyAI（repo 实名为 MonkeyCode / 百智办公）—— 企业 AI 工作台，但「开源」二字要打问号 ​

周刊转述：开源企业 AI 工作台 MonKeyAI（中文名「百智办公」），GitHub 已有 5000 颗星；可私有化部署，员工统一使用 AI、方便管理；可指定模型，共享知识库、技能、MCP 等资源，数据保留本地，提供管理后台做权限管理与使用统计；自带窗口支持办公 / 编程 / 设计三个核心场景，不需外部工具；客户端覆盖 Web / iOS / 安卓 / Mac / Win / Linux，甚至鸿蒙；服务端轻量——单核 CPU + 1G 内存的 Linux 服务器即可部署；免费使用，但团队超过 10 人需购买授权。

GitHub API 实测（2026-11-06）：chaitin/MonkeyCode — 描述「企业级 AI 办公工作台」；★4,996 / fork 762；AGPL-3.0；TypeScript；建库 2025-06-25；最后推送 2026-11-05（活跃）；open issues 409。核对结论：周刊写的「5000 颗星」准确（实测 4,996）；但周刊把项目名写成「MonKeyAI」，仓库实名为「MonkeyCode」——属转名失真，虽不严重，但检索时用 repo 名才找得到。

我的判断

  1. 这是本期唯一一条「企业级 agent 平台」类目，且它是本库长期缺的一块拼图。 本库已有的是个人外脑形态（cron + 知识库 + DSH harness），缺的是「组织级统一入口」——MonkeyCode 提供的三件东西正好是组织级的必需品：① 私有化部署 + 数据不出本地（合规）；② 共享知识库/技能/MCP（复用了本库已经在做的事，但把它从单人扩展到组织）；③ 管理后台做权限与用量统计（这是个人形态完全不需要、组织形态必须有的层）。 对金风科技 / 风电行业这类环境（数据敏感、有内网要求、需要统一管控），「单核 1G 就能部署」这个门槛低到几乎没有理由不试。
  2. 但「开源」这个词必须打问号——这是 AGPL-3.0 + 商业授权的混合体。 实测许可证是 AGPL-3.0，而周刊自己写明了「团队超过 10 人需购买授权」。这两条组合起来意味着：它是一个 open-core 商业产品，不是纯社区项目。 具体要注意两点：① AGPL 的传染性——若把它作为网络服务提供给外部，AGPL 要求对外提供源码，这对内部自用无碍、对做成对客服务则是硬约束；② 「10 人」这条线是商业条款，不是技术要求——所以对用户的实际含义是：小团队可以零成本自用，超过 10 人的组织要先算授权账。 本库此前记过的教训（#417 Cloud Mail 的 fork > star 反常）在这里不适用——fork 761 / star 4,990 比例正常，且 issue 数 409 说明社区在使用，不是刷量。
  3. 一个必须说明的不对称：它是「让全员用 AI」，而本库 #417 的结论是「不要让 AI 代表你」。 这两条不冲突，但必须在部署时把边界说清楚——MonkeyCode 的价值在**「统一入口 + 共享资源 + 权限管控」**（把 AI 使用从个人行为变成可治理的组织能力），而不是「把对外动作授权给 AI」。落地建议：接入时把「共享知识库」这一项对齐本库已有的知识网络（外脑的 topics/ 结构可以直接作为企业知识库的骨架），但严格限制任何会向外部第三方发起请求的 agent 能力——理由与 #417 评注 3 完全一致。

二、科技动态（5 条） ​

1. 一光日：旅行者 1 号（周刊转述，NASA 官方页面） ​

事实：旅行者 1 号将于 2026-11-18 抵达距地球一光日的位置，是人类第一个达到该距离的飞行器。它 1977-09-05 发射，光走一天，它走了 49 年 2 个月零 11 天。该时间 × 365 ≈ 1.8 万年，即它走完一光年所需时间；而离太阳最近的恒星比邻星是 4.24 光年。

评注：这是本期唯一的「纯尺度」条目，而它给出的尺度恰好是全篇最好的注脚。 1.8 万年走一光年 / 4.24 光年 —— 这两个数字把「太空机房」（主文 2）的野心的量级摊开了：人类最远的飞行器，还要 4.76 万年才能到最近的恒星系；而同期我们在讨论「把数据中心搬上轨道」——这两种「太空」不在同一个尺度上，轨道算力是「离地几百公里」，星际旅行是「离地几光年」，混为一谈就会高估前者。 更值得记下的是那条**「光需要走一天，它走了 49 年」**：通信延迟 1 天，意味着任何对旅行者 1 号的指令都无法实时交互——这正是「Agent 自主性」最纯粹的形态：当延迟大到人无法介入，就只能预先授权。 与本库 #417「不要让 AI 代表你」形成一个迷人的张力：在 1 天延迟的尺度上，除了「让它代表你」别无选择。

2. 英国关闭固话（The Register） ​

事实：英国宣布明年 1 月关闭固定电话，即淘汰铜线电话，只保留光纤/网线的数字电话。周刊补充：中国早就把模拟电话网淘汰，改用数字电话网，但光纤入户后光猫依然提供电话接口（RJ11），把数字信号转成模拟信号传给电话；英国这次是要淘汰 RJ11 接口的电话，完全改用数字电话和无线通信，并判断国内迟早也会这样做。

评注：这条技术上是「最后一公里的模拟残留被清理」，但真正有意思的是它揭示了基础设施换代的实际速度。 模拟电话网（PSTN）退役是一场持续几十年的替换，而它最终被清掉的不是「网络」而是「接口」——因为语音这件事早就在数字网络上跑完了，剩下的只有那根铜线两端的两块转换芯片。模式可迁移：任何旧系统的退役，最后被淘汰的都不是核心，而是「兼容层」。 这与本库 #415 的大小写：Deno 死于「Node 兼容性的引力井」——兼容层既是旧系统的续命装置，也是它无法真正死亡的证据。 对用户的直接相关性：这是「遗留接口的运维成本」类问题的教科书案例，与 topics/self-hosting/ 里「不暴露公网、减少攻击面」的取向一致（淘汰铜线 = 淘汰一个物理攻击面）。

3. JetBrains 亏损（helgilibrary） ​

事实：著名 IDE 厂商 JetBrains 2025 年亏损，是成立 20 年以来第一次亏损。主力产品 IntelliJ IDEA 是 Java/Kotlin 开发利器，绝大部分使用 Java 的公司都在用。周刊给的两种可能：① AI 编码盛行，传统 IDE 需求变少；② JetBrains 为 AI 投入巨资——「不管是哪一种原因，都反映了传统 IDE 正在衰落」。

文摘：人体体温在下降吗？（Yahoo News / 科学报道） ​

事实（周刊转述）：19 世纪 60 年代，德国医生卡尔·温德利希为定义「发烧是疾病还是症状」，在 15 年里定期收集 25000 名患者的腋下温度，获超一百万条数据，据此确定人体正常体温 37℃——我们今天的体温/发烧概念就源于他的研究。但近期研究发现人体正常体温似乎在下降：美国男性体温比 19 世纪低约 0.59℃，现在正常体温似乎应该是 36.39℃。

三种解释：① 人类整体健康状况大大改善——以前的人多有肺结核、牙病、痢疾、风湿热、骨髓炎，免疫系统长期对抗炎症导致体温升高；现在健康、炎症少，体温下降。② 生活环境温度变化——当代人室内生活舒适、常有空调，温度变化小，身体不用费力维持体温，消耗能量少，释放热量也少。③ 温德利希弄错了——19 世纪温度计不精确，有科学家认为他的温度计比现代高出 2℃，且他测的是腋下温度而非如今更常用的口腔温度，导致 37℃ 是高估值。

四个影响因素：（1）老年人体温较低（代谢减慢、活动减少）；（2）女性比男性体温高（周刊原文注明：「目前，关于这点还没有可信的」解释）；（3）清晨体温下降（凌晨 3–5 点最低，下午 4–6 点最高）；（4）身高与体重反比（体温随身高增加而降低——体表面积越大散热越多；随体重增加而略微升高）。

评注

  1. 这篇是本期最好的「测量学病例」，而且它的三种解释恰好构成一个完整的认知框架。 三种解释对应三类错误来源：① 真实变化（人群健康变了）；② 环境变化（生活条件变了）；③ 测量工具/方法变了（仪器与部位不同）。 「体温下降」这个现象，很可能不是三者之一，而是三者的叠加——而周刊最后列的四个影响因素（年龄、性别、时点、体型）其实是在说：所谓「正常体温」从来不是一个数，而是一个分布。 这直接呼应本库一条反复出现的主线（#414「判断被压成一个浮点数」）：把一个分布压成一个标量（37℃）来用，短期可行，长期必然出错。
  2. 最该留下的是解释 ③ 的方法论教训：一个用了 100 多年、写进全球教科书的常数，来源是一次可能系统性偏高的手测。 温德利希做了当时能做的最好的事——15 年、25000 人、100 万条数据——但 100 万条数据没有修正一个系统性偏差（温度计偏高 2℃ + 腋下测温）。 这是「数据量救不了系统性误差」的教科书案例，对本库的直接映射是：知识库里的结论，若来源工具本身有偏（某个有立场的博客、某次未经核实的转述），无论引用多少次都不会变得更对——这也是本库坚持「一手实抓 + 与周刊转述分开记账」的理由（#413 的 Spotify/Shopify、#414 的 RSA-896、#417 的 vals.ai 都是同一类教训）。**
  3. 「女性比男性体温高」后面那句「目前关于这点还没有可信的解释」值得单独表扬并留档。 作者（或周刊）宁可留下一个悬空的观察也不编解释——这是本库「如实说明不确定」原则的一个外部范本。 与之对照的是解释 ① 和 ②：它们同样是相关性叙述（健康状况 ↑ → 炎症 ↓ → 体温 ↓；空调普及 → 维持体温成本 ↓ → 体温 ↓），但至少给出了机制路径。 「有观察、无机制」时明确标注，是本条文摘最专业的一处。

#内容我的判断
1「真心，正义，无畏，同情。」（电影《无问西东》）本期唯一的非技术条目，且它出现的位置很巧妙——结尾前放一句道德箴言，是周刊的固定节奏（#417 是扎克伯格、#416 是职场言论）。但这一条与本期主文 1 形成了一组张力：「无畏」与「同情」在 21 世纪初的互联网上是现实社交的默认要求（你要面对面说话）；在今天的算法时间线里，它们变成了要对冲掉的东西——因为无畏和同情都不产生 engagement。 读法：它不必被当作鸡汤，可以当作对「优化目标错了」这句判词的补充——被优化掉的不只是摩擦，还有这四种品质。
2「民众在自己电脑上装内存，其实是一件很糟糕的事情。因为这些内存 95% 的时间都处于闲置状态，如果人们想要解决当前的内存供应问题，那就应该把内存都交给我们用在机房。」（山姆·奥特曼，OpenAI CEO）本期最需要拆的一条，而且它和本期主文 2（太空机房）是同一枚硬币：「算力必须集中到能效最高的地方」。逻辑上它有一半是对的：从「资源利用率」看，个人终端的闲置内存确实是浪费（这与云计算经济学的核心论点一致）。但它有一个致命的结构性跳跃：把「资源利用率」当成了唯一优化目标——个人拥有内存的价值不在利用率，而在「不受第三方调度」。用一句话概括这条的问题：它用「机房能效比更高」证明了「个人不该拥有算力」，但能效从来不是所有权存在的理由。 与 #417「闭源平台可单方面收回你的能力」形成完美闭环：如果内存都归机房，那么你的计算能力就完全取决于「机房里的人愿不愿意给你算」。 我的立场很明确：这条可以直接当作本库 topics/self-hosting/ 的引言来用——它把「为什么需要自托管」这个问题，从「隐私」抬高到了「是否还拥有算力」。
3「人们还没有充分认识到，既然电动汽车配备了大容量电池，为什么还要买个小电池仅仅为了应急？电动汽车其实是家庭的备用电源。」（《电网中断期间的双向充电》）这是本期与用户专业领域（风电 / PyPSA 能量仿真）直接相关的一条言论，而且它的洞察是真实的：电动车的车载电池（通常 40–100 kWh）比家用储能墙（通常 10–13 kWh）大一个量级，而它们 90%+ 的时间停在车位上。 技术上的关键前提是 V2H/V2L（vehicle-to-home/load）双向充电——这已经不是概念，而是部分车型的现有功能。对本库 energysim 的直接价值：它把「需求侧灵活性」从「可削减负荷」升级成「可反向供电的分布式储能」——PyPSA 建模里电动汽车从「柔性负荷」变成「分布式储能单元」，这会实质性改变容量规划的最优解。 但要标注三个现实约束（周刊未提）：① 电池循环寿命的隐性成本（用车的电池给房子供电 = 把电池寿命卖给电网，这笔账通常不划算）；② 车载双向充电器的成本与普及率；③ 电网侧需要允许并网反向送电的规范。 所以这条的正确定位是「方向明确、约束未解」，不是「即插即用的省钱方案」。
4「AI 生成的内容就像沥青，看起来光鲜明亮，而且很容易随处涂抹。但如果你以后需要清除沥青，即使一切顺利，也需要数年时间。」（《AI 帕斯卡的赌注》）本期最好的一个比喻，而且它的杀伤力在于「清除成本的不对称」。 注意它比较的不是「好/坏」，而是**「涂上去容易 / 铲下来极难」——这正好是本库 #415「生成便宜 ≠ 维护便宜」的视觉化版本，但比那一版更狠，因为它点出了「时间尺度」：数年的清除期。** 与本期主文 3（JS 框架的 AI 成本）形成完美互文：主文 3 用数字说了同一件事——代码量 ↑ → 未来每次编辑都更贵 → 维护是乘性的支出；而这条言论说的是「如果生成的东西是错的，那未来的每一次编辑都在给它补漆」。 对本库的操作含义很具体：知识库里「AI 生成的、未经核实的摘要」就是沥青——写入时零成本，日后要清理时得先弄清哪句是原文哪句是补充。 这正是本库坚持「一手实抓 + 明确区分周刊转述与我方评注」的工程理由。⚠️（顺带记一笔：「帕斯卡的赌注」这个标题本身很好——「先信了再说，反正不亏」的现代版是「先生成了再说，反正便宜」；而两者的失效方式相同：赌注成立的前提是「错的代价可承受」，而沥青告诉我们代价被推迟了，不是被取消了。）
