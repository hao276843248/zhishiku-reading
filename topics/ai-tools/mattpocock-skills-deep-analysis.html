Matt Pocock Skills：AI 编程的工程纪律 ​

来源：mattpocock/skills（GitHub，23k stars / 3 周）· LangLabs 官方文档 · CSDN 技术解构（2026-07-07） 整理：2026-07-09

零、身份确认 ​

  • 作者：Matt Pocock，Total TypeScript 创始人，TypeScript 领域顶级布道者
  • 项目：mattpocock/skills，MIT 开源
  • 数据：开源三周 23,000+ stars，60,000+ newsletter 订阅
  • 定位：Agent skills for disciplined software engineering — grilling, TDD, diagnosis, and architecture, not vibe coding

一、核心理念：模型越强，技能越简单 ​

这是理解 mattpocock-skills 的第一句话。"模型越强，技能越简单"——这与 GSD、BMAD、Spec-Kit 等"流程控制工具"形成了根本对立。

两个范式 ​

维度流程控制工具（GSD/BMAD）mattpocock-skills
核心理念控制流程，剥夺开发者控制权自由灵活，开发者掌握主导权
技能粒度大而全的流程（"做项目"）小而独立的技能（"做需求访谈"）
可组合性低——流程是线性固定步骤高——按需组合，顺序自由
可修改性低——修改流程 = 修改整个框架高——每个 SKILL.md 独立可改
信任模型不信任开发者（流程强制约束）信任开发者（技能是工具，不替代判断）
适用场景标准化、重复性强的项目需要快速迭代和灵活调整的开发

Pocock 的原话："Skills are designed to be small, easy to adapt, and composable. They work with any model. Hack around with them. Make them your own. Enjoy."

深层哲学：技能是"语法"，不是"剧本" ​

GSD 试图写一个"剧本"——规定每一步做什么、什么时候做、谁来做。Pocock 的技能是"语法"——定义了"怎么做"的模式，但"做什么"和"什么时候做"完全由开发者决定。

类比： GSD 是宜家说明书（第 1 步拧螺丝 A，第 2 步装面板 B），mattpocock-skills 是工具箱（锤子、螺丝刀、卷尺——按需取用，组合自由）。

二、四个失败模式：对"AI 工程学"缺失的诊断 ​

Pocock 在 README 中归纳了四个 AI 编码助手的失败模式。这不是抱怨——这是一位有数十年工程经验的开发者，把问题树和解决方案树逐层对齐的结果。

模式一：Agent 没做你想要的事 ​

引述：Pocock 引用《程序员修炼之道》——"没有人真正知道自己想要什么。"（David Thomas & Andrew Hunt）

本质：这不是 AI 的问题——这是人类沟通的根本问题。过去你面对的是一个能主动追问的人类开发者，现在你面对的是一个从不敢说"我不明白"的模型。AI 的"沉默"让含混的需求变成了致命的代码。

解决方案：强制开启结构化的追问环节（grilling session）——让 Agent 在写任何代码前，变成一位挑剔的架构师，从功能范围、边界条件、错误处理、性能要求、技术栈约束、测试策略等维度连续追问，直到所有模糊地带被扫清。

对应技能：

技能分类定位
/grill-meProductivity通用需求深访，非代码场景
/grill-with-docsEngineering工程级深访，附带领域语言建模和 ADR

模式二：Agent 表达过于啰嗦 ​

引述：Pocock 引用 Eric Evans《领域驱动设计》——"有了通用语言，开发者之间的对话和代码的表达都源自同一个领域模型。"

本质：不是 token 浪费的问题——是认知负载。当开发者和 AI 说不同的语言时，沟通成本是线性的，但理解偏差是指数的。Pocock 自己的例子：没有共享语言时，"课程中某个 section 下的 lesson 被赋予文件系统中的实际位置时出现问题"；有共享语言后，就是"物化级联（materialization cascade）出了问题"。

解决方案：CONTEXT.md —— 一个共享语言文件，Agent 在每次交互前读取。这不是两个独立功能的拼接，而是 grill-with-docs 的统一流程：在需求深访的过程中，同步提炼领域术语并写入 CONTEXT.md，同时将技术决策记录为 ADR。

Pocock 的评价：共享语言"可能是整个仓库中最酷的技术"——它带来的好处远超减少啰嗦本身：变量和函数的命名会自动收敛到一致风格；代码库对 Agent 来说变得更可导航；Agent 花费更少的 token 在"思考"上，因为它拥有了一套更精炼的语言系统。

模式三：代码跑不起来 ​

引述：Pocock 再次引用《程序员修炼之道》——"始终采取小而谨慎的步骤。反馈的频率就是你的速度上限。永远不要承担过大的任务。"

本质：反馈回路断了。人类程序员有持续的多层反馈：IDE 的静态检查、浏览器 DevTools、单元测试、甚至"这行写完感觉不对劲"的直觉。Agent 没有这些——它看到的只有 prompt 和自己生成的文本。

解决方案：显式重建多层反馈回路——静态类型 + 浏览器访问 + 自动化测试。在测试层面，红-绿-重构循环是关键纪律：Agent 必须先写一个会失败的测试，然后写最小的实现让它通过，再在有测试保护的前提下重构。

对应技能：

技能核心功能
/tdd红-绿-重构循环，按垂直切片推进，附 6 个参考文档
/diagnose结构化调试循环：复现 → 最小化 → 假设 → 插桩 → 修复 → 回归测试

工程判断内建：/tdd 不是简单地说"请用 TDD"，而是内建了具体的工程判断——测试应该验证公共接口而非实现细节；禁止水平切片（一次性写完所有测试再写实现），必须垂直切片（一个测试 → 一个最小实现 → 循环）。

模式四：我们造了一团泥球 ​

引述：Pocock 引用 Kent Beck（"每天都要投资于系统的设计"）和 John Ousterhout（"最好的模块是深的——它们允许通过简单的接口访问大量功能"）。

本质：这是前三个模式的总和与终局。Agent 没理解需求 → 反复修补 → 代码冗余堆积。Agent 没有共享语言 → 命名混乱 → 模块边界模糊。Agent 没有反馈回路 → bug 被埋在深处 → 越改越乱。

AI 时代的独特加速：Agent 加速编码的同时也在加速软件熵增——代码库以史无前例的速度变得复杂。

解决方案：三层防御机制——

时机技能作用
进入时/to-prd质询你将要触及哪些模块
过程中/zoom-out强制 Agent 在理解某段代码时将其放在整个系统的上下文中
恶化后/improve-codebase-architecture利用 CONTEXT.md 和 ADR，从泥球中发现"深模块"机会并逐步重建架构边界

Pocock 建议每隔几天就运行一次 /improve-codebase-architecture——这不是随意的经验之谈，背后是对"AI 让代码腐化不可逆"这一事实的诚实面对。

三、技能体系全景 ​

技能分类：User-invoked vs Model-invoked ​

这是 Pocock 技能体系中最精妙的设计之一：

  • User-invoked（用户调用）：你主动调用（如 /grill-me），其工作是"编排"——协调多个 Agent 行为
  • Model-invoked（模型调用）：你可以调用，Agent 也可以自动判断后调用；其工作是"可复用的纪律"

一个用户调用技能可以调用多个模型调用技能，但用户调用技能之间互不调用。 这保证了用户始终是决策者——Agent 不会在用户不知情的情况下"启动一个技能链"。

四、实战流程：从零构建秒杀系统 ​

视频演示的完整流程：

Idea → Research → Prototype → PRD → Kanban → Implementation → QA/Code Review

1. 项目初始化：/setup-matt-pocock-skills ​

一次性配置三个决策：

配置项选项默认
Issue TrackerGitHub Issues / GitLab Issues / 本地 MarkdownGitHub
Triage Labels5 个状态标签的自定义映射默认名称
Domain Docs单一上下文（单体项目）/ 多上下文（多模块）单一上下文

2. 需求访谈：/grill-with-docs ​

不是简单的"头脑风暴"——是结构化的深度访谈。Agent 从 6 个维度连续追问：

  • 功能范围（"这个功能包含什么？不包含什么？"）
  • 边界条件（"空输入怎么办？并发怎么办？"）
  • 错误处理（"失败了怎么恢复？"）
  • 性能要求（"期望的 QPS？P99 延迟？"）
  • 技术栈约束（"必须用 Redis 吗？"）
  • 测试策略（"哪些路径必须测试？"）

产出：CONTEXT.md（领域术语表）+ ADR（架构决策记录）

3. 生成 PRD：/to-prd ​

将访谈对话合成为结构化 PRD，包含：用户故事、实现决策、技术栈、数据库设计、API 路由。

4. 开发阶段：三种路径 ​

路径使用场景技能
直接开发需求清晰、改动小AI 读 PRD 后直接编码
计划驱动复杂改动、需要多步协调Claude Code Prime 模式
测试驱动核心逻辑、需要高可靠性/tdd

5. 原型设计（可选）：/prototype ​

  • 逻辑原型：可运行的终端应用
  • 设计原型：1-3 个 UI 方案，可切换预览

五、与 GSD 的对比：为什么"简单"赢了 ​

GSD 的失败模式 ​

GSD（Generate-Specify-Develop）试图通过规定流程来保证质量：

GSD: 需求 → 规格（必须）→ 开发（必须按规格）→ 测试（必须通过）

问题：流程越刚性，开发者越被动。 当需求变了（它一定会变），整个流程需要重新走一遍。当 Agent 在某个步骤卡住了，开发者没有工具来"跳过"或"调整"——只能等流程走完。

Pocock 的替代方案 ​

Pocock: 工具箱（grill / tdd / diagnose / prototype / to-prd / to-issues）

不是"少了流程"，而是"把流程的控制权还给开发者"。 你知道什么时候需要需求访谈，什么时候需要 TDD，什么时候需要原型——不需要一个框架来告诉你。

对齐我们的 SOUL 自进化原则 ​

Pocock 的"模型越强，技能越简单"与我们的自进化原则完全同构：

  • 我们的原则："能力要复用——重复出现的问题 → 沉淀为 skill，不要每次重做"
  • Pocock 的原则：每个 skill 是独立的、可修改的、可组合的——不是"流程"，是"模式"

技能的"简单"不是"简陋"——是"把复杂留给 Agent 的判断力，把控制留给开发者的判断力"。

六、与现有知识库的深度连接 ​

6.1 LLM Wiki / GBrain：CONTEXT.md 是 Agent 的知识库 ​

CONTEXT.md 是 LLM Wiki 的"微缩版"——它实现了"写入时编译"的核心思想：

维度GBrainCONTEXT.md
编译者LLM（Dream Cycle）LLM（grill-with-docs）
结构Compiled Truth + Timeline领域术语 + 架构约束
更新夜间自动每次需求访谈增量更新
使用检索时读取Agent 每次交互前读取

Pocock 的共享语言本质上就是 GBrain 的 Compiled Truth——"你相信什么"和"你为什么相信"被清晰分开。

6.2 认知萎缩：共享语言是对抗认知负债的疫苗 ​

核心连接：Pocock 的"模式二"（Agent 表达啰嗦）直接对应认知萎缩假说中的"系统熵增"——当 Agent 没有共享语言，每次交互都是从零建模，认知负载指数增长。

CONTEXT.md 是认知假体（cognitive prosthesis）——不是替代你的思考，而是让你和 Agent 共享同一个概念空间，避免"每次都要重新解释什么是物化级联"。

6.3 代码-状态分离（跨领域合成模式 #1） ​

技能体系：
  代码层 = SKILL.md（技能定义，不变）
  状态层 = CONTEXT.md + ADR（共享知识，持续演化）
  执行层 = Agent 的每次运行（实例化，临时）

与 LLM Wiki 的编译过程同构：原始文档（代码）→ 编译页面（状态）→ 查询时读取（执行）。

6.4 摩擦假说：Pocock 的技能是"战略性摩擦" ​

这是最深刻的连接。 Pocock 技能体系的每一个环节都在刻意增加摩擦：

技能增加的摩擦消除的摩擦
/grill-with-docs需求访谈（10-30 分钟）方向错误（数小时返工）
/tdd先写测试（5-15 分钟）回归 bug（数小时排查）
/diagnose结构化调试（15-60 分钟）随机修补（数天累积）
/improve-codebase-architecture定期扫描（30-60 分钟/周）架构腐化（数月重构）

Pocock 不是"增加摩擦"——他是"把摩擦放在正确的位置"。 在需求阶段投入 30 分钟摩擦，省去开发阶段 3 小时的方向错误。这完全符合我们的 Friction Hypothesis 核心论点：不是所有摩擦都是坏的——关键摩擦是"认知免疫系统"，消除它会导致系统性脆弱。

6.5 激活函数进化：从"开关"到"旋钮" ​

时代开发流程激活函数
传统瀑布模型（线性、不可逆）Sigmoid（二值开关）
敏捷Scrum（迭代、可调整）ReLU（半开关）
GSD流程控制（强制步骤）硬截断
mattpocock-skills可组合工具箱（按需取用）SwiGLU（连续旋钮）

mattpocock-skills 是 AI 开发流程的 SwiGLU 化——从"你必须走这几步"到"你可以按需组合这些技能"。

6.6 PentAGI 的知识图谱：技能体系的"经验积累" ​

PentAGI 用 Graphiti + Neo4j 跨任务积累攻击经验。mattpocock-skills 用 CONTEXT.md + ADR 跨会话积累领域知识。两者都是"持久化记忆"——Agent 不会在每次对话后重置。

  1. 引入"共享语言"概念——为每个 topic 创建类似 CONTEXT.md 的术语表

  3. 引入"垂直切片"思想——知识整理按"一个主题一个文件"推进，而非"一次整理所有主题"

七、历史平行 ​

工匠的工具箱 → 宜家的说明书 → AI 的"技能工具箱" ​

时代范式代表
前工业工匠的工具箱（每个工匠有自己的工具，按需取用）学徒制
工业流水线说明书（标准化流程，工人不可偏离）福特制
敏捷Scrum 框架（流程 + 灵活性的折中）Jira
AI 时代（GSD）机器人流程（Agent 严格执行步骤）GSD/BMAD
AI 时代（Pocock）工匠的工具箱回归（Agent 按需调用技能）mattpocock-skills

Pocock 的"技能工具箱"是前工业时代工匠精神的数字回归——不是"流程自动化"，而是"判断力增强"。

类型系统 → 技能系统 ​

Pocock 是 TypeScript 布道者——这并非偶然。TypeScript 的核心思想是"在编译时捕获错误，而不是运行时"。mattpocock-skills 的核心思想是"在需求访谈时捕获错误，而不是在编码时"。

技能之于 AI 交互，如同类型系统之于代码——在错误的代价还很小的时候，把它找出来。

八、核心判断 ​

  1. "模型越强，技能越简单"不是口号，是工程洞察。 当模型足够强，它不需要被"管"——它需要被"引导"。技能不是"替代判断"，是"增强判断"。

  2. 四个失败模式构成了一条因果链：需求错位 → 沟通冗余 → 质量缺失 → 架构腐化。每一个模式的解决方案对应一类技能，技能之间又通过共享数据（CONTEXT.md、ADR）相互关联。这不是巧合——这是工程学。

  3. Pocock 的技能是"战略性摩擦"。 在需求阶段投入 30 分钟，省去开发阶段 3 小时的方向错误。这与我们的 Friction Hypothesis 完全同构——不是所有摩擦都是坏的，关键摩擦是免疫系统。

  4. CONTEXT.md 是 LLM Wiki 的微缩版。 共享语言 = 编译后的知识。每次交互前读取，每次需求访谈后更新——"写入时编译，查询时读取"。

  5. "技能"不是"剧本"——它是"语法"。 GSD 是剧本（固定步骤），Pocock 是语法（可组合模式）。这决定了 AI 开发工具的最终形态——不是"管住 AI"，是"让 AI 和开发者说同一种语言"。

  6. 与我们的系统高度互补。 我们的系统有深度分析（跨领域连接、历史平行、反事实推演），Pocock 有工程纪律（grill、TDD、diagnose、architecture）。两者结合 = 理想的知识工作技能体系。
